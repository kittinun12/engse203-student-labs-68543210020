# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

เอกสารอธิบายการออกแบบฐานข้อมูลเชิงสัมพันธ์ โครงสร้างตาราง เหตุผลในการออกแบบ และผลการทดสอบข้อกำหนดความถูกต้องของข้อมูล (Constraints) สำหรับระบบ Campus Service Request

---

## 1. ภาพรวม

ระบบ Campus Service Request ได้รับการออกแบบโดยใช้รูปแบบ **ฐานข้อมูลเชิงสัมพันธ์ (Relational Database)** แบ่งข้อมูลออกเป็น 2 ตารางหลัก ได้แก่ ตาราง `users` (ผู้ใช้งาน/ผู้แจ้ง) และตาราง `requests` (คำร้องขอรับบริการ)

```
┌──────────────────────────┐               ┌──────────────────────────────────────┐
│          users           │               │               requests               │
├──────────────────────────┤               ├──────────────────────────────────────┤
│ PK  id (INTEGER)         │◄──────┐       │ PK  id (TEXT)                        │
│     name (TEXT)          │       └───────┼─ FK requester_id (INTEGER)           │
│     department (TEXT)    │  1         N  │     request_type (TEXT)              │
│     email (TEXT, UNIQUE) │               │     location (TEXT)                  │
└──────────────────────────┘               │     details (TEXT)                   │
                                           │     priority (TEXT)                  │
                                           │     status (TEXT)                    │
                                           │     created_at (TEXT)                │
                                           └──────────────────────────────────────┘
```

### ประเภทความสัมพันธ์
- **ความสัมพันธ์แบบหนึ่งต่อหลาย (One-to-Many หรือ 1:N):**
  - ผู้ใช้งาน 1 คน (`users`) สามารถสร้างคำร้องได้หลายรายการ (`requests`) หรืออาจยังไม่เคยสร้างคำร้องเลยก็ได้ (ความสัมพันธ์ฝั่ง requests มี Cardinality เป็น `0..*`)
  - คำร้องแต่ละรายการ (`requests`) ต้องเป็นของผู้ใช้งานคนใดคนหนึ่งเท่านั้น และต้องมีผู้รับผิดชอบคำร้องเสมอ ไม่สามารถเป็นคำร้องลอยที่ไม่มีเจ้าของได้ (ความสัมพันธ์ฝั่ง users มี Cardinality เป็น `1..1`)
- **การเชื่อมโยงข้อมูล:**
  - เชื่อมโยงผ่าน `users.id` ซึ่งเป็น **Primary Key (PK)** ของตาราง `users` เข้ากับ `requests.requester_id` ซึ่งทำหน้าที่เป็น **Foreign Key (FK)** ของตาราง `requests`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ในสัปดาห์ที่ 06–07 ระบบเดิมจัดเก็บข้อมูลในไฟล์ JSON แบนราบ (Flat JSON) โดยเก็บชื่อผู้แจ้ง (`requesterName`) รวมอยู่ในทุกคำร้อง วิธีดังกล่าวทำให้ข้อมูลผู้ใช้และข้อมูลคำร้องปะปนอยู่ในที่เดียวกัน ซึ่งก่อให้เกิดปัญหาสำคัญต่อความถูกต้องและความสมบูรณ์ของข้อมูลในระยะยาว

### ตอบคำถาม: "ถ้าสมชายเปลี่ยนชื่อ ต้องแก้กี่ที่"
- **ถ้าใช้โครงสร้างเดิม (ไม่แยกตาราง):** หากสมชายสร้างคำร้องไว้ 10 รายการ แล้วสมชายทำการเปลี่ยนชื่อหรือแก้ไขข้อมูลส่วนตัว เราจำเป็นต้องตามไปแก้ไขชื่อในคำร้อง **ครบทั้ง 10 ที่** หากระบบเกิดข้อผิดพลาดหรือแก้ไขไม่ครบ ข้อมูลในระบบจะเกิดความขัดแย้งกันทันที (Data Inconsistency)
- **เมื่อแยกเป็น 2 ตาราง (โครงสร้างปัจจุบัน):** ข้อมูลของสมชายจะถูกจัดเก็บไว้ที่ตาราง `users` เพียงแห่งเดียว (Single Source of Truth) เมื่อสมชายเปลี่ยนชื่อ เราทำการแก้ไข **เพียง 1 ที่เท่านั้น** คือแถวของสมชายในตาราง `users` (`UPDATE users SET name = '...' WHERE id = 1;`) และเมื่อมีคำสั่งเรียกดูคำร้องด้วย `JOIN` ทุกคำร้องของสมชายจะแสดงชื่อใหม่อย่างถูกต้องและสม่ำเสมอทันทีทั้งระบบ

### ปัญหาของโครงสร้างแบบเดิมและการแก้ไขด้วยการแยกตาราง

1. **ปัญหาข้อมูลซ้ำซ้อน (Data Redundancy):**
   - *โครงสร้างเดิม:* ทุกครั้งที่ผู้ใช้คนเดิมสร้างคำร้องใหม่ ข้อมูลชื่อ สังกัด และอีเมลของผู้ใช้จะถูกบันทึกซ้ำลงไปทุกครั้ง ทำให้สิ้นเปลืองพื้นที่จัดเก็บ และหากระบบมีคำร้องนับหมื่นรายการ ข้อมูลผู้ใช้จะซ้ำซ้อนกันมหาศาล
   - *การแก้ไข:* แยกข้อมูลผู้ใช้ออกมาเก็บที่ตาราง `users` เพียงชุดเดียว และในคำร้องเก็บเพียงรหัสตัวเลข `requester_id` ขนาดเล็กเพื่อชี้โยงเท่านั้น
2. **ปัญหาความผิดปกติในการแก้ไข (Update Anomaly / แก้ไม่ครบ):**
   - *โครงสร้างเดิม:* หากผู้ใช้ย้ายภาควิชาหรือเปลี่ยนชื่อ การอัปเดตจะต้องวนลูปแก้ไขทุกระเบียนคำร้องในระบบ หากเกิดข้อผิดพลาดระหว่างทาง (Network หลุด หรือ Process ตายกลางคัน) จะทำให้คำร้องบางใบแสดงสังกัดเก่า และบางใบแสดงสังกัดใหม่
   - *การแก้ไข:* อัปเดตข้อมูลผู้ใช้ที่ตาราง `users` จุดเดียว ข้อมูลคำร้องทั้งหมดที่อ้างอิง `requester_id` ดังกล่าวจะสะท้อนข้อมูลล่าสุดโดยอัตโนมัติ
3. **ปัญหาความผิดปกติในการเพิ่มและลบข้อมูล (Insertion & Deletion Anomaly):**
   - *Insertion Anomaly:* หากมีอาจารย์หรือนักศึกษาใหม่เข้ามาในคณะ แต่บุคคลนั้นยังไม่เคยแจ้งคำร้องใดๆ ระบบเดิมจะไม่สามารถบันทึกข้อมูลบุคคลนั้นลงระบบได้ เพราะไม่มีคำร้องให้ผูก
   - *Deletion Anomaly:* หากผู้ใช้คนหนึ่งมีคำร้องเพียงรายการเดียว แล้วคำร้องนั้นถูกลบออกจากระบบ ข้อมูลประวัติการติดต่อและอีเมลของผู้ใช้นั้นจะสูญหายไปจากระบบด้วย
   - *การแก้ไข:* เมื่อแยกตาราง เราสามารถเพิ่มผู้ใช้ใหม่ลงใน `users` ได้ทันทีแม้จะยังไม่มีคำร้อง และการลบคำร้องใน `requests` จะไม่กระทบต่อข้อมูลบุคคลใน `users`
4. **ปัญหาการพิมพ์สะกดผิดและข้อมูลไม่สอดคล้องกัน (Data Inconsistency & Typos):**
   - *โครงสร้างเดิม:* การกรอกชื่อหรือภาควิชาเป็นข้อความอิสระในทุกคำร้อง นำไปสู่การพิมพ์ผิด เช่น "วิศวกรรมซอฟต์แวร์" บ้าง "วิศวกรรมซอฟแวร์" บ้าง ทำให้เวลาจัดกลุ่มทำรายงานสรุปแยกตามภาควิชา ระบบนับเป็นคนละภาควิชา
   - *การแก้ไข:* บันทึกสังกัดที่ถูกต้องไว้ในตาราง `users` เพียงครั้งเดียว การสรุปผลและจัดกลุ่มจะมีความแม่นยำ 100%

## 3. รายละเอียดตาราง

### ตาราง `users` (ผู้ใช้งานระบบ)

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraints) | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | ใช้เป็น Surrogate Key รหัสตัวเลขจำนวนเต็มเรียงลำดับอัตโนมัติ ประหยัดพื้นที่จัดเก็บ มีประสิทธิภาพสูงสุดในการทำ B-Tree Indexing และสะดวกต่อการนำไปใช้อ้างอิงเป็น Foreign Key |
| `name` | `TEXT` | `NOT NULL` | ชื่อและนามสกุลของผู้ใช้ เป็นข้อมูลระบุตัวตนสำคัญที่ระบบต้องมีเสมอเพื่อใช้แสดงผลและติดต่อประสานงาน จึงห้ามเป็นค่าว่าง |
| `department` | `TEXT` | `NOT NULL` | ภาควิชาหรือหน่วยงานสังกัด จำเป็นต่อการคัดกรองงาน การกำหนดสิทธิ์ และการทำสถิติสรุปภาพรวม จึงต้องระบุเสมอ |
| `email` | `TEXT` | `NOT NULL UNIQUE` | อีเมลสำหรับติดต่อกลับ ต้องไม่เป็นค่าว่าง และต้องไม่ซ้ำกันในระบบ (`UNIQUE`) เพื่อป้องกันการลงทะเบียนบัญชีผู้ใช้ซ้ำซ้อน และใช้เป็น Unique Identifier ในการยืนยันตัวตน |

### ตาราง `requests` (คำร้องขอรับบริการ)

| คอลัมน์ | ชนิดข้อมูล | ข้อกำหนด (Constraints) | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | ใช้รหัสเชิงธุรกิจ (Natural / Business Key) เช่น `REQ-001` เพื่อให้ผู้ใช้ เจ้าหน้าที่ หรือผู้บริหาร สามารถจดจำ สื่อสาร และอ้างอิงหมายเลขใบแจ้งซ่อมได้อย่างชัดเจน |
| `requester_id` | `INTEGER` | `NOT NULL`, `REFERENCES users(id)` | Foreign Key เชื่อมโยงไปยัง `users.id` เพื่อรักษา Referential Integrity ห้ามเป็น `NULL` เพื่อรับประกันว่าทุกคำร้องต้องมีผู้รับผิดชอบที่ระบุตัวตนได้จริง |
| `request_type` | `TEXT` | `NOT NULL`, `CHECK (request_type IN ('แจ้งซ่อม','บริการบัญชีผู้ใช้','ขอใช้อุปกรณ์','อื่น ๆ'))` | ประเภทของคำร้อง กำหนดค่าตายตัวด้วย CHECK constraint เพื่อควบคุมมาตรฐานข้อมูล ป้องกันข้อผิดพลาดจากการพิมพ์ และสะดวกต่อการจัดหมวดหมู่งาน |
| `location` | `TEXT` | `NOT NULL` | สถานที่เกิดเหตุหรือห้องที่ต้องการรับบริการ เป็นข้อมูลจำเป็นอย่างยิ่งเพื่อให้เจ้าหน้าที่สามารถลงพื้นที่ปฏิบัติงานได้ถูกต้อง |
| `details` | `TEXT` | `NOT NULL` | รายละเอียดและอาการของปัญหา เป็นข้อมูลสำคัญในการประเมินและวางแผนแก้ไขปัญหา จึงห้ามปล่อยว่าง |
| `priority` | `TEXT` | `NOT NULL DEFAULT 'normal'`, `CHECK (priority IN ('normal','urgent'))` | ระดับความเร่งด่วนสำหรับจัดลำดับความสำคัญของงาน กำหนดค่าเริ่มต้นเป็น normal และจำกัดค่าที่ยอมรับได้ด้วย CHECK |
| `status` | `TEXT` | `NOT NULL DEFAULT 'pending'`, `CHECK (status IN ('pending','in-progress','completed'))` | สถานะวงจรชีวิตของงาน กำหนดค่าเริ่มต้นเป็น pending เมื่อรับเรื่องเป็น in-progress และเมื่อเสร็จสิ้นเป็น completed ควบคุมด้วย CHECK ป้องกันการใส่สถานะที่ไม่ถูกต้อง |
| `created_at` | `TEXT` | `NOT NULL DEFAULT (datetime('now','localtime'))` | บันทึกวันและเวลาที่ส่งคำร้องโดยอัตโนมัติตามเวลาเครื่อง เพื่อใช้จัดลำดับคำร้องตามไทม์ไลน์ และคำนวณระยะเวลาแก้ไขปัญหา (SLA) |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

### 1. ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน (INTEGER vs TEXT)
- **`users.id` ใช้ `INTEGER` (Surrogate Key):**
  - ผู้ใช้งานไม่จำเป็นต้องมีรหัสที่ต้องสื่อความหมายต่อภายนอก การใช้ตัวเลขจำนวนเต็มแบบ `AUTOINCREMENT` ช่วยให้ฐานข้อมูลจัดการสร้างรหัสให้โดยอัตโนมัติ
  - ใช้พื้นที่จัดเก็บน้อย (4-8 bytes) และเปรียบเทียบค่าได้เร็วกว่าข้อความมาก เหมาะสำหรับการนำไปทำ Index และใช้เป็นจุดเชื่อมต่อ (Foreign Key) ในการทำ `JOIN`
- **`requests.id` ใช้ `TEXT` (Business / Semantic Key):**
  - คำร้องเป็นเอกสารทางธุรกิจที่ต้องมีการสื่อสารระหว่างมนุษย์ (เช่น นักศึกษาแจ้งช่างว่า "ติดตามใบคำร้อง REQ-005")
  - การใช้รูปแบบ Prefix + รหัสตัวเลข เช่น `REQ-001` ช่วยสื่อความหมายทันทีว่าเป็นรหัสประเภทใด และสามารถขยายรูปแบบรหัสในอนาคตได้ง่าย (เช่น แยกประเภทเป็น `FIX-001`, `ACC-002`)

### 2. ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว (Defense in Depth)
- **หลักการป้องกันหลายชั้น (Defense in Depth):** การตรวจสอบข้อมูลที่ Web API (Validation Middleware) เป็นการตรวจที่ด่านหน้าจากคำขอที่เข้ามาทาง HTTP แต่ API ไม่ใช่ช่องทางเดียวที่ข้อมูลจะเข้าสู่ฐานข้อมูลได้
- **ความเสี่ยงที่ API ป้องกันไม่ได้:**
  - ผู้ดูแลระบบ (DBA) หรือนักพัฒนาอาจรันคำสั่ง SQL โดยตรงเพื่อจัดการข้อมูลเร่งด่วน
  - การรันสคริปต์ Migration ข้อมูล, งานประมวลผลเบื้องหลัง (Background Worker / Batch Job), หรือการ Import ข้อมูลจากระบบอื่น
  - โค้ดของ API อาจมีข้อผิดพลาด (Bugs) หรือมี Route ใหม่ที่ลืมใส่ Middleware ตรวจสอบข้อมูล
- **ฐานข้อมูลคือปราการด่านสุดท้าย (Single Source of Truth of Integrity):** การกำหนด `CHECK` constraint ในระดับฐานข้อมูล จะรับประกันว่าข้อมูลที่ผิดพลาดจะไม่มีทางถูกบันทึกลงสู่พื้นที่จัดเก็บอย่างเด็ดขาด ไม่ว่าข้อมูลนั้นจะส่งผ่านมาทางใดก็ตาม

## 5. ตัวอย่างการใช้ JOIN

คำสั่ง SQL สำหรับดึงข้อมูลคำร้องพร้อมชื่อผู้แจ้ง สังกัด และสถานะ:

```sql
SELECT r.id,
       u.name AS requester_name,
       u.department,
       r.request_type,
       r.location,
       r.status
FROM requests r
JOIN users u ON u.id = r.requester_id
ORDER BY r.id;
```

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

### เปรียบเทียบผลของ JOIN กับข้อมูลที่ API ส่งให้ React (Week 07)

- **ผลจากการทำ SQL JOIN:**
  ```text
  REQ-001 | สมชาย ใจดี | pending
  ```
- **ข้อมูล JSON ที่ API ส่งให้ React (Week 07):**
  ```json
  {
    "id": "REQ-001",
    "requesterName": "สมชาย ใจดี",
    "status": "pending"
  }
  ```

### ข้อสังเกตเชิงสถาปัตยกรรม
1. **ความเข้ากันได้ของรูปทรงข้อมูล (Data Shape Compatibility):**
   - เมื่อเราเขียนคำสั่ง `JOIN` แล้วกำหนด Alias คอลัมน์เป็น `u.name AS requesterName` ข้อมูลแต่ละแถวที่ส่งคืนจากฐานข้อมูลจะมีชื่อฟิลด์และโครงสร้างตรงกับ JSON Object เดิมที่ React คาดหวังใน Week 07 พอดี
   - ทำให้ฝั่ง Frontend (React UI) ไม่จำเป็นต้องรับรู้เลยว่าหลังบ้านมีการปรับเปลี่ยนฐานข้อมูลจากไฟล์ JSON มาเป็นฐานข้อมูลเชิงสัมพันธ์
2. **การแยกความรับผิดชอบตามสถาปัตยกรรมแบบแบ่งชั้น (Separation of Concerns):**
   - ฐานข้อมูลทำหน้าที่ Normalization เพื่อจัดเก็บข้อมูลอย่างมีประสิทธิภาพและป้องกันความซ้ำซ้อน
   - Service Layer ใน Node.js ทำหน้าที่ประกอบ (Denormalize via JOIN) และแปลงผลลัพธ์เป็น DTO (Data Transfer Object)
   - Presentation Layer (React) ทำหน้าที่แสดงผลข้อมูลตามที่ได้รับ
3. **การเปลี่ยนแปลงเฉพาะใน Service Layer (Zero Frontend Impact):**
   - ในสัปดาห์ที่ 10 เราจะสามารถนำคำสั่งจาก `queries.sql` ไปใส่ใน `requestService.js` ได้โดยตรง โดยแก้ไขเพียงฟังก์ชันอ่านและเขียนข้อมูลใน Service Layer เท่านั้น
   - ส่วนประกอบอื่นๆ เช่น Controller, Routes และ React Components ทั้งหมดจะยังคงทำงานได้ตามเดิม 100% โดยไม่ต้องแก้ไขโค้ดเลย

## 7. ผลการทดสอบ Constraint (CP25)

เพื่อพิสูจน์ว่าฐานข้อมูลสามารถปฏิเสธข้อมูลที่ไม่ถูกต้องได้จริง (Negative Testing) ได้ทำการทดสอบข้อกำหนดทั้ง 5 รูปแบบกับฐานข้อมูลจริงที่เปิดใช้งาน `PRAGMA foreign_keys = ON;` โดยมีผลการทดสอบดังนี้:

### ① Foreign Key Constraint
- **วัตถุประสงค์:** ป้องกันการบันทึกคำร้องที่อ้างอิงไปยังรหัสผู้ใช้ที่ไม่มีอยู่จริงในระบบ
- **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details)
  VALUES ('REQ-FAIL1', 99999, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ Foreign Key');
  ```
- **ผลลัพธ์:**
  ```text
  FOREIGN KEY constraint failed
  ```
- **สรุปผล:** ✓ ถูกปฏิเสธจริง เนื่องจาก `requester_id = 99999` ไม่มีอยู่ในตาราง `users`

---

### ② CHECK Constraint
- **วัตถุประสงค์:** ป้องกันการบันทึกสถานะที่อยู่นอกเหนือจากข้อกำหนด (`'pending'`, `'in-progress'`, `'completed'`)
- **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details, status)
  VALUES ('REQ-FAIL2', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ CHECK', 'ยกเลิก');
  ```
- **ผลลัพธ์:**
  ```text
  CHECK constraint failed: status IN ('pending','in-progress','completed')
  ```
- **สรุปผล:** ✓ ถูกปฏิเสธจริง เนื่องจากค่า `'ยกเลิก'` ไม่ตรงกับเงื่อนไขใน CHECK constraint

---

### ③ UNIQUE Constraint (อีเมลผู้ใช้)
- **วัตถุประสงค์:** ป้องกันการสร้างผู้ใช้ใหม่ด้วยอีเมลที่ซ้ำกับคนที่มีอยู่แล้วในระบบ
- **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO users (name, department, email)
  VALUES ('สมชาย อีกคน', 'วิศวกรรมไฟฟ้า', 'somchai@rmutl.ac.th');
  ```
- **ผลลัพธ์:**
  ```text
  UNIQUE constraint failed: users.email
  ```
- **สรุปผล:** ✓ ถูกปฏิเสธจริง เนื่องจากอีเมล `somchai@rmutl.ac.th` มีผู้ใช้งานอยู่แล้ว

---

### ④ UNIQUE / Primary Key Constraint (รหัสคำร้อง)
- **วัตถุประสงค์:** ป้องกันการสร้างคำร้องที่มีรหัส `id` ซ้ำกับคำร้องเดิม
- **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details)
  VALUES ('REQ-001', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ Primary Key ซ้ำ');
  ```
- **ผลลัพธ์:**
  ```text
  UNIQUE constraint failed: requests.id
  ```
- **สรุปผล:** ✓ ถูกปฏิเสธจริง เนื่องจาก `REQ-001` ถูกใช้งานเป็น Primary Key ไปแล้ว

---

### ⑤ NOT NULL Constraint
- **วัตถุประสงค์:** ป้องกันการสร้างคำร้องโดยไม่ระบุสถานที่ (`location`) ซึ่งเป็นข้อมูลจำเป็น
- **คำสั่งที่ทดสอบ:**
  ```sql
  INSERT INTO requests (id, requester_id, request_type, location, details)
  VALUES ('REQ-FAIL5', 1, 'แจ้งซ่อม', NULL, 'ทดสอบ NOT NULL');
  ```
- **ผลลัพธ์:**
  ```text
  NOT NULL constraint failed: requests.location
  ```
- **สรุปผล:** ✓ ถูกปฏิเสธจริง เนื่องจากคอลัมน์ `location` มีข้อกำหนด `NOT NULL`
